# T43. Как NPC проходят через двери с загрузкой — результат

Ветка: feature/interior-portal (без кода) · Версия сборки: нет · Статус: исследование

## Что выяснено
Подробно — `docs/NPC_DOORS.md`. Контроль поведения игры — 0.8.27, 318–460 с (F8 выкл.): те же стеки и то же затемнение 0,5 с.
- **Проход — всегда `TESObjectDOOR::Activate` (`AE#17922`, слот `0x37`)**. Перенос — `SetPosition` в маркер `ExtraTeleport` (`+0x5BA`) и `MoveRefToNewSpace` (`AE#19799`, `+0x63A`), не `MoveTo` и не `SetParentCell` напрямую (**по коду**).
- **Путь через дверь — один на обе ячейки.**
  - Узел двери несёт `MovementMessageActivateDoor` (`AE#91958`), за ним идут узлы дальней ячейки.
  - Путь строит `BSPathBuilder::Build` (`AE#91713`) → `AE#91717` → узлы дверей `AE#91750` → `AE#91674`; дальний отрезок — от связанной двери, без маркера (пачка 1, сверено координатором). `TeleportDoorSearch` (`AE#30933`) — грубый маршрут по дверям для игрока, карты, патруля, квестов, не путь NPC.
- **Сообщения пути** разбирает `AE#37892` по таблице `AE#38103`: `ActivateDoor` → `AE#37878`, `WarpToLocation` → `AE#37877` → `AE#37313`, `ApproachingDoor` → `AE#37889`.
- **Не high:** `Job_Low_messages` `AE#39071` → `AE#41297` → `AE#41717` → `AE#37892` → `AE#37878+0x1ED` → `ActivateRef` → `Activate` → перенос сразу. **В игре:** 420 стеков, все на рабочих потоках, двери по всему Скайриму.
- **High** (**по коду + в игре**, 22 пары):
  1. `AE#37878` запускает действие `kActionActivate` (`AE#39255`, `+0x1AA`) и запоминает дверь в `HighProcessData+0xD8`.
  2. Дверь активирует `ActionActivateDoneHandler` (`AE#42866`) или пакет (`AE#39637` → `AE#39408`).
  3. `Activate` ставит `fadeState=kTeleportOut` (`AE#39454`, `+0x4EB`) и возвращает 0.
  4. Через 0,49–0,50 с `AE#39457+0x1FB` (из `Actor::UpdateNonRenderSafe`, задание `ProcessActorAnimSG`) активирует снова, и идёт перенос. Затем `kTeleportIn`, если `AE#37503` = 0.
  5. `OnActivate` приходит один раз: на второй активации `ActivateRef` его обходит (`+0x197`, `+0x37F`).
- **Потоки.** 465 из 474 вызовов `Activate` со стеком — рабочие потоки. `MoveRefToNewSpace` там безопасен: Havok идёт через `TaskQueueInterface` (`AE#36932`/`36921`/`36933`). `ActivateRef` берёт общий спин-замок `AE#401080`.
- **События NPC** — только из `MoveRefToNewSpace`:
  - `OnLocationChange` (`+0x8A2`), если локация сменилась;
  - `OnAttachedToCell`/`OnDetachedFromCell` (`+0x986`), если подключённость ячеек разная;
  - `CLOC` и `BGSActorCellEvent` — только игрок (`xrefs` `AE#32288`, `AE#41034`). `Actor::SetParentCell` (`AE#37304`) событий не шлёт.
- **Опускание с дверью в руке** (`AE#37624+0x135`, главный поток): затемнение начинается, переноса нет — 9 из 9 случаев в 0.8.28–0.8.30. Контроля нет.

## Главное для T20, T21 и шага 6
- **Бесшовный проход** = преобразование портала + `AE#37313(actor, pos, rot, cell|null, world|null, stop=0)` на главном потоке.
  - **Уточнение координатора, 09.11.2026 (пачки 2 и 3):** основной путь — как у ванильной двери (`SetPosition`, поворот, `MoveRefToNewSpace`): `AE#37313` даёт второй `OnLocationChange` при переносе внутри одного мира. Ходок пути после скачка может повторно послать `ActivateDoor` — гасить для этой двери (`NPC_DOORS.md`, 6 и 9).
  - Запасной вариант: `SetPosition` + `MoveRefToNewSpace`, как ветка не high в `Activate`, без `StopMovement`.
  - Не должны сработать: анимация (`AE#39255`), затемнение (`AE#39454`, `AE#37889`, `AE#39457`), маркер (`AE#17922+0x5AD…+0x63A`), `ExtraBadPosition`, `StopMovement`.
- **Перехват:** detour `AE#37878` (оба уровня, рабочие потоки: только запрос) и свой детектор плоскости в тике (П7). `Activate` слот `0x37` — страховка для пакетов и скриптов.
- **T20:** удерживаемый интерьер должен быть подключён (`cellState` ≥ 6), иначе нет Havok и придёт `OnDetachedFromCell`. **T11:** вошедший с улицы middleHigh поднимется с перестановкой `AE#37618`; `AE#41717` бросает очередь при смене желаемого уровня.
