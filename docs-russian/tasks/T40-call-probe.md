# T40. Сборка-зонд: какие функции движка работают, когда и на каком потоке

Этап 2, инструмент для T38 и T39. Ветка `task/T40-call-probe`, worktree `..\CLR-T40` с сабмодулем. Код: новый модуль `src/CallProbe.*` и одна строка в `Hooks::Install` (правило T28 в `Hooks.h`), расширение `Profiler`. Прогон: да, один общий для T38 и T39. Поведение игры не меняет. Модель — Opus 5.5, усилие — high. Бриф обновлён 08.11.2026 по итогам T38, T39 и массового чтения.

## Зачем

T38 и T39 построили карты по коду (`docs/PLAYER_MAP.md`, `docs/CELL_LOADING_MAP.md`). Три вопроса код не решает, а от них зависят T20, T21 и T29. Зонд отвечает на них и заодно считает, что работает на каждой фазе перехода.

- **В1. Идут ли задания загрузки одновременно с главным потоком.**
  - `CellLoaderTask::PostProcess` (`AE#18529`) → `TES::BufferCell` (`AE#13434`) → выгрузка `AE#13721` выполняются и на потоках `BSJobs` (`Job_IO`, `AE#39084` → `AE#36565` → `AE#75705`).
  - Кадр `Main::Update` (`AE#36564`): `SetJobTaskEvent(1…4)` (`AE#69514`) на `+0x82F…+0x859`, `WaitForJobTask(0,1)` (`AE#69516`) на `+0x8B3`, только если `AE#35406(1)`.
  - Нужно знать, что делает главный поток в момент вызова этих функций с другого потока. От ответа зависит, безопасен ли наш detour `AE#13721`: сейчас он решает по состоянию главного потока.
- **В2. Обновляется ли игрок дважды за кадр.**
  - Главный поток: `Main::Update+0x2A7` → `AE#36581` → vfunc `0xAD` (`PlayerCharacter::Update`).
  - Задание: `UpdateActor` (`AE#41448`) → `AE#41369+0x2A6` → тот же слот `0xAD`.
  - Нужно счесть вызовы `AE#41369`, у которых `this == [AE#403521]`.
- **В3. Откуда в старых трассах 44 вызова `DetachAll` (из `AE#13295+0x64`) не на главном потоке.**
  - По коду загрузка сохранения целиком идёт на главном потоке (`results/T38-T39-batches.md`, «T39, пачка 1»). Другой поток бывает один раз — при старте (`InitTESThread`, `AE#36644`).
  - Есть два предположения:
    - старая трасса определяла главный поток неверно: `Trace::IsMainThread` берёт `RE::Main::threadID`;
    - эти вызовы шли при выходе в меню или из игры (`docs/FINDINGS.md`, строка с «выход из игры (`DetachAll` от `AE#13295`)»).

## Сделать

1. **Счётчики вызовов** по списку ID из INI (`[CallProbe] sIDs=…`, по умолчанию список выше).
   - При загрузке найти все прямые вызовы (`E8 rel32`) на адрес из Address Library во всём `.text`.
   - Каждый вызов перенаправить на заглушку своего места. Заглушка считает вызов по месту, виду потока и окну, затем делает `jmp` в цель. Длина инструкции не меняется, вход функции не трогается: чужие detour на входе не мешают. Счёт по местам сразу показывает, кто вызывает.
   - **Вызовы через vtable** — патчем слота (список выше). Если стоит наш vfunc-перехват, заглушка оборачивает его.
   - **Функции без прямых вызовов** (задания `BSJobs`, указатели в таблицах данных, например `Job_IO` `AE#39084` и `AE#39055`) — найти ссылки на них в данных (`ghidra_xrefs`) и патчить указатель. Если указателя нет — detour входа, если вход не занят. Иначе — 0 мест, и это строка в отчёте.
   - Место, где `E8` ведёт не туда (чужой `write_call`, наш перехват) или байты изменились после скана, пропустить и счесть по причине. В отчёт идут найдено, пропатчено и пропущено по ID и причинам.
2. **Вид потока без API в заглушке.**
   - ID потока читать из TEB (`gs:[0x48]`).
   - Вид брать из таблицы «ID потока → вид» фиксированного размера. Заполнять её вне заглушек:
     - главный поток — по своему захвату: поток загрузки плагина и поток хука `PlayerCharacter::Update`, сверить с `RE::Main::threadID` (В3);
     - IO — из `CellLoaderTask::Run`;
     - `BSJobs` и прочие — перечислением потоков по клавише и при старте, по адресу старта потока (`NtQueryInformationThread`, `ThreadQuerySetWin32StartAddress`) с сопоставлением с базой.
   - Неизвестный поток — вид «прочие» и отдельный счёт его ID.
3. **Метки главного потока для В1.**
   - Заглушки мест внутри `Main::Update` на главном потоке пишут номер места в атомарную переменную «где главный поток».
   - Заглушки `AE#18529`, `AE#13434`, `AE#13721`, `AE#75705` на других потоках добавляют счёт в гистограмму «где был главный поток».
   - Отдельно счесть вызовы, пришедшие, пока главный поток внутри `AE#69516` (`WaitForJobTask`) или вне кадра.
4. **Проверки для В2 и В3.**
   - В заглушке `AE#41369` сравнивать `rcx` с `[AE#403521]`.
   - Для `AE#13295` и `DetachAll` (слот 1 `GridCellArray`, вызов `AE#13295+0x64`; база — `GridArray::DetachAll` `AE#15939`) писать в трассу каждый вызов: поток по своему захвату, `RE::Main::threadID`, контекст (идёт загрузка сохранения, выход в меню, выход из игры — по событиям или флагам, которые уже есть в трассе).
5. **Окна.**
   - По фазам перехода, как у `Profiler`.
   - По клавише: N секунд обычной игры (улица, интерьер, портал).
   - **Свободных F-клавиш нет:** F1 занят T32, F2, F3, F4, F6, F7, F8 заняты. Возьми сочетание с модификатором (например `Shift+F6`) или клавишу вне F, код задаётся в INI. Проверь `Settings` и `Events.cpp`.
6. **Профилировщик всех потоков** (если хватит бюджета; иначе — в «Открытые вопросы»). Сэмплы IO-потоков и `BSJobs` по клавише и под экраном загрузки. Правила `Profiler` из `CLAUDE.md`, раздел 7: между `SuspendThread` и `ResumeThread` без кучи и логов.
7. **Отчёт** в трассу (`callprobe`, `profile` с потоком) и сводка в `tools/run_digest.py`:
   - вызовы за кадр по ID, виду потока и окну;
   - 10 самых частых мест вызова на ID;
   - гистограмма В1, счёт В2, список В3.

   Имена по ID в скрипте берутся из TSV базы; в плагине имён нет.
8. **INI.** Всё выключено по умолчанию (`bEnabled=0`): без него ничего не патчится, поведение как без зонда. Список ID и клавиша — для прогона.
9. **Накладные расходы.** Время кадра с зондом и без на одном месте. Если какая-то функция слишком частая (например `AE#19812`), её можно исключить через INI.
10. Версия в `xmake.lua` +1, архив `dist/`, `tar -tf`.

## Правила

- `CLAUDE.md`, раздел 7. Не в главном потоке — только счётчики, никаких обращений к `TES`. В заглушках нет вызовов API, кучи, блокировок и логирования; счёт — атомарным сложением или по потокам.
- **`PlayerReads.*` не править.** Общие части (блок заглушек над образом, скан `rel32`) вынеси в новый `src/CodePatch.*`. Перевод `PlayerReads` на них — отдельным коммитом после слияния обеих задач.
- Оба модуля ставятся последними в `Hooks::Install`; T40 после T32. Места T32 (`mov`/`cmp` с указателем игрока) и места T40 (`E8`) — разные инструкции. Проверь, что включённые вместе `bCensus=1` и `bEnabled=1` не задевают друг друга. Это пункт проверки, но не обязательный режим прогона.
- Адреса только через `RELOCATION_ID`/`REL::ID`. Зонд — исследовательский, только AE. Если SE-номера нет, запиши строку в `docs/PORTABILITY.md`.
- Псевдокод в git, docs и результат не класть: только выводы, `AE#id`, смещения.
- Прогон с Engine Fixes — в конце этапа, не здесь.

## Как проверить в игре (шаги для результата, ≤ 6)

1. Установить архив, `[CallProbe] bEnabled=1`, Engine Fixes выключен. Перед запуском — `python tools/ghidra/gq.py stop`.
2. Загрузить сохранение у «Гарцующей кобылы». Окно по клавише на улице, 20 с.
3. Войти в таверну, окно 20 с внутри, выйти. Фазы перехода пишутся сами.
4. Пройтись по Вайтрану со сменой ячейки сетки; `coc Riverwood`.
5. F8 (портал), окно 20 с у двери.
6. Загрузить сохранение, выйти в главное меню, выйти из игры (В3). Логи — в `logs\run-<версия>\`.
