# T36. NG types in the Ghidra database: structures, vtables, `this`, and singletons — result

Branch: task/T36-ghidra-types · Build version: none (no plugin code) · Status: ready to merge; database updated (main project and read-only copy)

## What was found
- **Compiler instead of a C++ parser.** NG headers build with MSVC only with `ENABLE_SKYRIM_AE`. In this branch, NG itself lays out classes for AE: `TES` = 0x2C0 with fields 0x128–0x2B8 (in the SE+AE build they are hidden behind `GetRuntimeData()`), `PlayerCharacter` = 0xBE8 (matches `Allocate(…, 0xBE8)` in T31). Every `STATIC_ASSERT_SIZE` checks the AE size: compilation succeeded, so all 188 `STATIC_ASSERT_SIZE` and 2,719 `static_assert(sizeof…)` in NG are correct for AE.
- **Sources:** `/d1reportAllClassLayout` — sizes, bases, vtables with method names (16,087 classes, 3,005 tables). A DLL with one function per `RE::` class (3,228; 11 private nested classes discarded) → `NG.pdb`, 11 MB, with types for all fields. Ghidra's PDB loader in types-only mode (`DATA_TYPES_ONLY`, `applyNoAnalysisState`) → 8,649 structures, 30,831 fields, 22 s.
- **`this`:** Ghidra looks up a class structure by namespace path; the preferred program root `/NG/RE` maps `TES` → `/NG/RE/TES`. `__thiscall` was applied to 6,910 virtual functions and 479 with an NG name; 93 were skipped (static according to NG headers, 548 in total, or an analysis-derived name) and 73 (the class has no structure). Another 617 were already `__thiscall`.
- **Vtables:** if bases are embedded whole, `vfptr` resides in the most-base structure, and derived-class slots remain unnamed in pseudocode. Therefore, for 1,435 classes with their own primary table, the primary-base chain is expanded into flat fields, and `vfptr` at +0 points to `/NG/vftables/<Class>_vftable` (1,793 tables, 31,495 slots). Secondary bases are nested `super_<Base>` (3,410).
- **Verification:**
  - `AE#13316`: `SetCurrentCell(TES* this)`, fields `interiorCell`, `interiorBuffer`, `exteriorBuffer`, `gridCells`, `worldSpace`, `currentGridX/Y`, `allowUnusedPurge`; call `gridCells->vfptr->DetachAll`.
  - `AE#40466`: `PlayerCharacter* this`, fields `parentCell`, `formID`, `extraList`, `locationMap`, call `vfptr->MoveHavok`. `AE#19130`: `objRoot->vfptr->DetachChild2` (slot 0x38, as in FINDINGS).
  - Sizes: all 5,433 `RE::` structures match the MSVC layout. Initially 55 were 4–8 bytes shorter: disabling packing lost tail padding, which step 6 restores.
- **`PlayerCharacter`:** in NG's AE build, the player block is replaced by the `_padPlayerRuntimeData` stub (0x3E0, 0x808). A `PLAYER_RUNTIME_DATA` of the same size was substituted in its place. NG's AE layout is for 1.6.629–1.6.1170: it lacks the 1.7.99 base (`BSTEventSink<BSSystemEvent>`), and `TES` has the 1.6.1130+ block.
- **Singletons:** 79 of 80 (`TES*` at `AE#403450`, `PlayerCharacter*` at `AE#403521`, `BSTimer` is the object itself). `RenderTargetManager` (`AE#411451`) is the object itself, contrary to NG (`CLAUDE.md`, section 7). The unsuccessful one is `hkContainerHeapAllocator` (the address is occupied by other data).
- **Ghidra does not delete `/NG`** when types are already in use: `removeCategory` fails after 2.5 min. Therefore, a rerun starts from the `<project>-pre-types` copy (`--restore`).
- **Vtable slot count: NG versus the game** (RTTI in the database, 1,321 classes without templates): 1,229 matched, 92 differ.
  - NG has fewer slots in 73 classes: input handlers `*Handler` (2 versus 7), `bhkSimpleShapePhantom` (2 versus 51), `BSSystemUtility` (2 versus 19), `hk*`, and others. Slots beyond NG are unnamed in the table.
  - NG has more slots in 19 classes: `*ActorPackageData` (10 versus 9), `*CameraState` (17 versus 16), `DialogueMenu` (12 versus 9). Ghidra may have determined the table to be shorter than it is. Verification is needed (T34).
- **Timing:** `collect_types.py` 30 s, `apply_types.py` 35 s, `snapshot.py` seconds.

## Open questions
- Signatures from NG `decltype` (parameter types) have not been applied: `this` is present, and the decompiler infers the remaining parameters.
- `SkyrimVM::_padVMRuntimeData` (0x554) is shorter than `VM_RUNTIME_DATA` (0x558): it remains a stub. Discrepancy in NG.
- Templates (`BSTEventSink<…>` and similar) received types only as fields and bases; methods in Ghidra template namespaces (`BSTEventSink<TESActivateEvent>`) were not matched with `/NG` (73 misses).
- 1.7.x and 1.5.97 need their own entry in `gconfig.VERSIONS` and a run (`collect_types.py` takes `runtime` from there).
