# T43. How NPCs pass through load doors — result

Branch: feature/interior-portal (no code) · Build version: none · Status: research

## What was found
Details — `docs/NPC_DOORS.md`. Game-behavior control — 0.8.27, 318–460 s (F8 off): the same stacks and the same 0.5 s fade.
- **Passage is always `TESObjectDOOR::Activate` (`AE#17922`, slot `0x37`)**. Transfer is `SetPosition` to the `ExtraTeleport` marker (`+0x5BA`) and `MoveRefToNewSpace` (`AE#19799`, `+0x63A`), not `MoveTo` and not `SetParentCell` directly (**from code**).
- **The path through a door is shared across both cells.**
  - The door node carries `MovementMessageActivateDoor` (`AE#91958`), followed by nodes in the far cell.
  - The path is built by `BSPathBuilder::Build` (`AE#91713`) → `AE#91717` → door nodes `AE#91750` → `AE#91674`; the far segment starts from the linked door, without the marker (batch 1, verified by the coordinator). `TeleportDoorSearch` (`AE#30933`) is a coarse door route for the player, map, patrols, and quests, not an NPC path.
- **Path messages** are processed by `AE#37892` using table `AE#38103`: `ActivateDoor` → `AE#37878`, `WarpToLocation` → `AE#37877` → `AE#37313`, `ApproachingDoor` → `AE#37889`.
- **Non-high:** `Job_Low_messages` `AE#39071` → `AE#41297` → `AE#41717` → `AE#37892` → `AE#37878+0x1ED` → `ActivateRef` → `Activate` → immediate transfer. **In the game:** 420 stacks, all on worker threads, doors throughout Skyrim.
- **High** (**from code + in the game**, 22 pairs):
  1. `AE#37878` starts the `kActionActivate` action (`AE#39255`, `+0x1AA`) and stores the door in `HighProcessData+0xD8`.
  2. The door is activated by `ActionActivateDoneHandler` (`AE#42866`) or a package (`AE#39637` → `AE#39408`).
  3. `Activate` sets `fadeState=kTeleportOut` (`AE#39454`, `+0x4EB`) and returns 0.
  4. After 0.49–0.50 s, `AE#39457+0x1FB` (from `Actor::UpdateNonRenderSafe`, `ProcessActorAnimSG` job) activates it again, and transfer occurs. Then `kTeleportIn`, if `AE#37503` = 0.
  5. `OnActivate` arrives once: on the second activation, `ActivateRef` bypasses it (`+0x197`, `+0x37F`).
- **Threads.** 465 of 474 `Activate` calls with a stack are on worker threads. `MoveRefToNewSpace` is safe there: Havok goes through `TaskQueueInterface` (`AE#36932`/`36921`/`36933`). `ActivateRef` takes the shared spin lock `AE#401080`.
- **NPC events** come only from `MoveRefToNewSpace`:
  - `OnLocationChange` (`+0x8A2`), if the location changed;
  - `OnAttachedToCell`/`OnDetachedFromCell` (`+0x986`), if cell attachment differs;
  - `CLOC` and `BGSActorCellEvent` — player only (`xrefs` `AE#32288`, `AE#41034`). `Actor::SetParentCell` (`AE#37304`) sends no events.
- **Lowering with a door in hand** (`AE#37624+0x135`, main thread): the fade starts, but there is no transfer — 9 of 9 cases in 0.8.28–0.8.30. There is no control.

## Key points for T20, T21, and step 6
- **Seamless passage** = portal transformation + `AE#37313(actor, pos, rot, cell|null, world|null, stop=0)` on the main thread.
  - **Coordinator clarification, 09.11.2026 (batches 2 and 3):** the main path is the same as a vanilla door (`SetPosition`, rotation, `MoveRefToNewSpace`): `AE#37313` produces a second `OnLocationChange` when transferring within the same world. The path walker may send `ActivateDoor` again after the jump — suppress it for this door (`NPC_DOORS.md`, 6 and 9).
  - Fallback: `SetPosition` + `MoveRefToNewSpace`, like the non-high branch in `Activate`, without `StopMovement`.
  - Must not trigger: animation (`AE#39255`), fade (`AE#39454`, `AE#37889`, `AE#39457`), marker (`AE#17922+0x5AD…+0x63A`), `ExtraBadPosition`, `StopMovement`.
- **Hook:** detour `AE#37878` (both levels, worker threads: request only) and our own plane detector in the tick (P7). `Activate` slot `0x37` is a safeguard for packages and scripts.
- **T20:** the held interior must be attached (`cellState` ≥ 6), otherwise there is no Havok and `OnDetachedFromCell` will arrive. **T11:** a middleHigh entering from the street will be promoted with `AE#37618` rearrangement; `AE#41717` drops the queue when the desired level changes.
