Branch: exp/T38-player-map (files written in the main folder) · Build version: none (no code) · Status: research, steps 1–6; step 7 (run) — with T40

## Findings
Tables — `docs/PLAYER_MAP.md`. Everything is based on the 1.6.1170 code (Ghidra database) unless stated otherwise.

1. **Paths to the player:** pointer `AE#403521` (2,838 references), second pointer `AE#401069` (549, T32), handle `AE#403520` (111), `formID == 0x14` (2 places: `GetCurrentLocation` `AE#19812` and `SetStartingPosition` `AE#19668`, both concerning `currentLocation`). New: a virtual path — `GetIsPlayerOwner` in the `ActorValueOwner` subobject (`AE#208050` slot 8, `AE#40691`, always 1).
2. **Class:** 14 vtables according to RTTI. Primary `AE#208040`: 107 `Character` overrides + 5 new slots (`0x12A`–`0x12E`). The secondary vtables contain 14 slots of their own, including 4 sinks (menu, menu mode, input, statistics). Only 13 overrides read `AE#403521` themselves (`Update`, `SetParentCell`, `FinishLoadGame`, `DropObject`, `UpdateRefLight`, `GoToPrison`, `ServePrisonTime`, `PayFine`, `CheckValidTarget`, `InitiateGetUpPackage`, `AE#40687`, `AE#41258`, `AE#40740`); 3 read the handle.
3. **The player's location for quests is a single field.** `currentLocation` (`+0xAD0`) is written only by `SetParentCell` (`AE#40466+0x19B`), the constructor (`AE#40411+0xE39`), and the loading screen `AE#51929` (temporarily, `+0xCA` → `+0x325`). For the player, `GetCurrentLocation` returns this field rather than the location of their cell. Location substitution (T32, D′) does not affect it.
4. **The player's `SetParentCell` does more than `CLOC`:** it also handles `BGSActorCellEvent` (region, music, water, HUD), climate, grass, camera (`AE#50833`), Havok, world map markers (`AE#40671`), and the world boundary. Everything is global and designed for a single player cell.
5. **Threads and order:**
   - `Main::Update` (`AE#36564`) `+0x6E` → `AE#40438`: teleport from `queuedTargetLoc` and `PositionPlayerEvent`; at the end (`+0x839`), processing of the Story Manager queue (`AE#32484`). Main thread. This answers the question in `LOCATION_TRIGGERS.md`, item 2.
   - Then `+0x2A7` → `AE#36581`: `PlayerCharacter::Update` (`+0xAD`), cell boundary crossing (`AE#19411` → vfunc `0x98`), `TES` grid shift based on the player position (`+0x201` → `AE#13288`). Main thread.
   - Animation (`Job_Player_animation` `AE#39055` → `AE#41371` → vfunc `0x7D`) and movement (`UpdatePlayerMovementJob` `AE#41445` → `AE#37350`) are separate `BSJobs` jobs.
6. **The NPC processing level “around the player”** means attaching grid cells whose center is the player position: `AE#13288` → `AE#19063+0x2C0` → `AE#19280+0xCF` vfunc `0x91` `DoMoveToHigh` for each reference. There is no separate radius in this path. For the portal (5.14, items 1–2), keeping the cell attached is sufficient: this is what `InteriorSim` does.
7. **More copies of the player's location:** `AE#404241`…`AE#404243` (`AE#40730`, iteration over actors within radius 700 — `AE#40807`, `AE#40817`, `AE#40818`); `cachedWorldSpace` `+0x630` and `exteriorPosition` `+0x638` (world map).
8. **Subsystems (name-based heuristic):** actor 637 places, UI 473, AI 258, forms and activation 208, input 165, Papyrus 164. The second pointer (`cmp`) is used only by gameplay logic; the UI does not read it.
9. **Incorrect database names:** `AE#403520` is named `gBarterMenu_TargetRefHandle` (it is the player handle); `AE#37350` is `PlayerCharacter::AE_37350` in the database and `Character::Update` in the docs, but it is movement for any actor (called by both movement jobs).
