# T35. Interface to the Ghidra database (MCP, skill, reader agent) — result

Branch: task/T35-ghidra-mcp · Build version: none (no plugin code) · Status: ready to merge; `.mcp.json` and `.claude/` are not installed (the user has not yet consented), templates are in `tools/ghidra/claude/`

## What was found
- **MCP tools** (`tools/ghidra/mcp_server.py`, stdio, JSON-RPC 2.0, stdlib, protocols 2024-11-05…2025-06-18; starts the Ghidra server itself):
  - `ghidra_decompile(targets, marks?, addr_prefix?, max_lines?, context?)`: a function of up to 150 lines is returned as text; longer functions return a file and excerpts of ±10 lines around marks with file line numbers.
  - `ghidra_asm`, `ghidra_xrefs`, `ghidra_info`, `ghidra_fieldrefs` — as in `gq.py`; `ghidra_status`.
  - `ghidra_search(name_regex | string_regex, kinds?)` — symbols (excluding `AE_<id>` labels, 173,523) and strings (37,125), each with `AE#`, reference count, and first locations (calls first, excluding `.pdata`/`UNWIND_INFO`).
  - `ghidra_callgraph(target, callers|callees, depth, max_nodes)` — tree with `AE#` and call offsets; upward includes vftable slots, downward includes indirect-call counts.
  - `ghidra_vtable(class, offset?)` — using MSVC RTTI (COL → subobject offset, CHD → bases); the slot is compared with the base's primary table: `inherited` / `override of …` / `new in …`.
  - `ghidra_struct(name)` — type layout from the database; NG types are not yet present (T36), so it returns a list of similar names.
- **Verification against known data:** `vtable PlayerCharacter` — 14 tables (`AE#208040`…`AE#208066`), primary has 303 slots, base `Character`; slot `0x98` (`+0x4C0`) = `PlayerCharacter::SetParentCell` (`AE#40466`), override of `Actor::SetParentCell` (`AE#37304`) — matched T15. `search SetParentCell$` found three implementations and the call to `Actor::SetParentCell` from `AE#40466+0x236`.
- **Pool and cache:** up to 3 decompilers (`CLR_GHIDRA_DECOMPILERS`), requests run in parallel (the global T33 lock was removed), and the program is read-only. Pseudocode cache — in memory (400 functions) and on disk at `%TEMP%\clr-ghidra\cache\<version>-<snapshot>\`; the snapshot is a hash of the copy's `*.gbf`/`*.prp` files (`~index` files change on every opening, even read-only).
- **The parallel decompiler does not corrupt responses:** 48 functions without cache, one at a time, then with 3 and 6 threads — all 48 files are byte-identical; 6 different commands and 12 decompilations simultaneously — all responses equal the sequential ones.
- **Measurements** (warm server unless otherwise stated):

| What | Time |
|---|---|
| First MCP call (server startup) | 7.5 s (including ~2 s for `connect` refusal to a closed port on Windows) |
| MCP overhead | 20–30 ms (`info` 0.03 s) |
| `decomp` / from cache (memory, disk) | 0.1–0.7 s / 0.02–0.05 s; disk cache survives restart |
| 48 functions without cache: 1 thread / 3 / 6 | 3.5 / 1.5 / 1.4 s |
| 3 decompilations in parallel through MCP | 0.7 s (individually 0.06–0.7 s) |
| `search`: first name / string index, subsequent | 6.3 / 6.0 s, then 0.1 s |
| `vtable PlayerCharacter`, `callgraph` depth 3 | 0.2 s, < 0.1 s |

- **Server memory:** 0.43 GB after startup, 0.67 GB with search indexes, 1.2 GB after ~160 decompilations; `decompile.exe` uses 8–9 MB each.
- **What subagents see — not verified:** without `.mcp.json` (or `claude mcp add`), the server is not connected in chats. According to Claude Code's design: a subagent without a `tools` field inherits all tools, including MCP; agent templates list `mcp__ghidra__ghidra_*` explicitly.
